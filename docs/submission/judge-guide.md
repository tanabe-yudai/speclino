# 審査員向けデモ手順

本番の SpecLino と GitHub のデモ PR を使い、上から順に操作すると主な機能をひととおり確かめられる手順です。
各手順には「操作」と「確かめること」を書いています。

- **所要時間**: 本編（1〜11）は約 20 分です。付録 A の手元の CLI（任意）は、さらに約 10 分かかります
- **必要なもの**: PC のブラウザ（Chrome 推奨）と、提出フォームに記載したテストアカウント（メールアドレスとパスワード）
- **URL**
  - SpecLino: https://speclino-web-6h5m3svkja-an.a.run.app
  - リポジトリ: https://github.com/tanabe-yudai/speclino
- **テストアカウントの権限**: ワークスペース `tanabe-yudai` の「メンバー」です。閲覧、下書きの編集、AI との会話はできます。
  承認・確定・トークンの発行など、オーナーと承認者だけの操作はできません。画面にはその旨の案内が出ます

> **お願い（共有の環境です）**
> - 「下書きを保存」「下書きに保存」「下書きを作る」は押さないでください。押しても配信と検査には影響しませんが、
>   ほかの審査員の画面に「承認待ち」として残ります
> - 検査詳細の「再実行」は押さなくても結果を確かめられます。再実行は 1 日の回数枠を全員で共有しています
> - 本文を書き換えても、保存しなければ何も残りません。画面を離れれば元に戻ります

## 画面の言葉

判定は 4 値です。画面と GitHub では次の日本語で表示します。

| 画面の表示 | 内部の値 | 意味 | ゲート（マージの可否） |
| --- | --- | --- | --- |
| 適合 | VERIFIED_IN_SCOPE | 解析の範囲で、仕様どおりであることを示せた | 止めない |
| 違反 | VIOLATED | 仕様に反する経路があり、反例（具体的な条件）がある | 止める |
| 未検証 | UNKNOWN | 解析できなかった・対応が無い。確認できないものを「適合」とは言わない | 必須の要求なら止める |
| 要確認 | REVIEW | 人の判断が要る（AI 支援の規約、設定の変更など） | 必須の要求なら、承認者が確定するまで止める |

- **知識**: チームがコーディングエージェントに渡すもの、つまり仕様・スキル・指示書（AGENTS.md / CLAUDE.md）・規約の 4 種類です
- **bundle**: 承認のたびにできる、有効な知識の集合です。署名つきの連番で、検査と配信は bundle の番号で固定します
- **ゲート**: PR に付く GitHub の Check `SpecLino / gate` です。必須の要求に違反・未検証・要確認が残ると「失敗」になります

## 1. ログイン（1 分）

1. https://speclino-web-6h5m3svkja-an.a.run.app を開きます。紹介ページ（LP）が表示されます
2. 右上の「ログイン」を押します（https://speclino-web-6h5m3svkja-an.a.run.app/login を直接開いても構いません）
3. 「メールアドレス」と「パスワード」に、提出フォームに記載したテストアカウントを入力して「ログイン」を押します

**確かめること**: ワークスペース `tanabe-yudai` のホーム（`/w/tanabe-yudai`）が開きます。

- 「メールアドレスまたはパスワードが正しくありません」と出た場合は、前後の空白を除いて入力し直してください
- 画面の上部に、次の項目が並びます。

  ```
  ホーム / 仕様 / スキル / 指示書 / 規約 / 検査 / 観測 / 設定
  ```

  画面幅が狭い場合は、下のタブ（ホーム・仕様・検査・観測・その他）になります。この場合、スキル・指示書・規約・設定は「その他」の中にあります

## 2. ホーム: チームが今やること（1 分）

ホームを上から順に見ます。

1. **やること**: ゲートが失敗の PR（デモ PR 3 本）などが並びます
2. **知識**: 「仕様」「スキル」「指示書」「規約」の 4 枚のカードに件数が出ます
3. **プロジェクトの健全性**: リポジトリ `speclino` の状態と、最新の検査の PR 番号・ゲートが出ます
4. **最近の検査**: PR ごとの検査が新しい順に並びます

**確かめること**: 4 種類の知識と、検査の状態が 1 つの画面にまとまっていることを確かめます。

## 3. 知識の一覧（1 分）

1. 上部の「**仕様**」を押します
   - 「ワークスペース全体の仕様」と「リポジトリ別の仕様」の 2 つの節に分かれて並びます
   - 各行には、名前（例: `spec-sys-001`）、範囲（「チーム共通」かリポジトリ名）、状態（例: 「有効 改訂 4」）が出ます
2. 上部の「**スキル**」を押し、`speclino-mcp-guide` を確かめます
3. 上部の「**指示書**」を押し、`agents-global` を確かめます

**確かめること**: 仕様・スキル・指示書が、同じ形（改訂番号と状態）で管理されていることを確かめます。
このリポジトリ自身の設計書（仕様 8 本）も、ここで管理しています。

## 4. 仕様のエディタ: Markdown と厳格な UML（3 分）

1. 「仕様」の一覧で `spec-sys-001` の名前を押します。エディタが開き、「プレビュー」が選ばれた状態で表示されます
2. プレビューを下へスクロールして、次を確かめます
   - 要求の表（`R-SYS-01` …）
   - Mermaid の図（クラス図・アクティビティ図など）
   - 「9. 実行の配置」の少し前にある、アクティビティ図 `gate-decision`（ゲートの決定の流れ）
   - プレビューの上に「問題なし」と出ていること（診断 0 件）
3. **わざと誤りを入れて、診断を出します。** 本文の欄の上の「**本文**」を押して、編集欄に切り替えます
4. ブラウザの検索（Ctrl+F、Mac は ⌘F）で `not before.triage.has_mandatory` を探します。次の行です

   ```
   c2 -->|"[e4] not before.triage.has_mandatory"| f
   ```

5. この行の `has_mandatory` を `has_required` に書き換えます（`not before.triage.has_required` にします）
6. 「**プレビュー**」を押します。ボタンの表示は「プレビュー（診断 N）」に変わっています

**確かめること**:

- 「エラー 1 件」と出ます。「診断の内容」を開くと、行と列つき（図 `gate-decision`）で `E_UNKNOWN_REFERENCE`「ガードの参照 before.triage.has_required を属性・domain の変数に解決できない」が出ます。クラス図の `Triage` に無い属性を書いたためです
- 診断を押すと、本文のその行へ移ります
- 仕様の図は、決定的な parser が読める部分集合だけを受け付けます。読めない書き方は、AI が補うことなく必ずエラーになります
- 確かめたら、手順 5 の書き換えを元に戻します（`has_mandatory` に戻すか、ページを再読み込みします）。**保存はしません**

> 画面の上部にある「改訂の履歴と差分」から、過去の改訂の差分と承認者を見られます。
> 仕様の場合は「整形した本文の差分」と「意味の差分」も出ます。
> 「承認」の欄には「承認できるのはオーナーと承認者です。」と出ます。メンバーは承認できません。

## 5. AI と作る: 質問で要件を詰め、書き換えを提案する（4 分）

AI（Vertex AI の Gemini と ADK）は、執筆の相談相手です。変換と判定には関わりません。

1. 手順 4 の `spec-sys-001` のエディタで、「**AI と作る**」パネルを確かめます
   - メンバーには最初から開いた状態で出ます。閉じている場合は、上部の「AI と作る」を押します
2. 入力欄（「AI への発言（今の編集欄の本文も一緒に送ります）」）に、たとえば次の文を入力して「**送る**」を押します

   ```
   ゲートが失敗したとき、PR のコメントに失敗の理由を必ず書く、という要求を足したい
   ```

3. 返答を待ちます（数十秒）。「考えています・・・」「調べたこと」の表示が順に出ます
4. 返答の下に「**AI からの質問**」と選択肢のボタンが出たら、どれか 1 つを押します。選んだ文がそのまま送られます
5. 返答に「下書きの提案があります」「本文に反映しました」などの行が出たら、「**差分を見る**」を押します

**確かめること**:

- AI はすぐに書き換えず、まず選択肢つきの質問で要件を詰めます
- 提案は本文の差分として出ます。編集欄に入っても「まだ保存していません。」と表示され、保存と承認は人が行います
- 提案を当てた本文にも、手順 4 と同じ診断がかかります。診断のエラーがある提案は、本文に反映されません
- 「出典」には、AI が調べた先（承認済みの知識・リポジトリ・Web）が出ます
- 確かめたら、ページを再読み込みして変更を捨てます。**保存はしません**。会話はあなたにだけ見え、ほかのメンバーには見えません

> 返答の代わりに「返答を得られませんでした」と出ることがあります。原因は、AI の 1 日の費用枠（デモ環境の上限）です。
> その場合は手順 6 以降へ進んでください。判定とそのほかの画面は AI なしで動きます。

## 6. GitHub: デモ PR のゲート（ログイン不要、4 分）

デモ PR は 3 本です。どれも「単体テストは通る」か「一見無害」な変更ですが、`SpecLino / gate` が失敗します。
番号は PR の題（デモ1・3・4）に合わせています。デモ2・5 はありません。

| PR | 題 | 変更 | ゲートを止めた必須ルール |
| --- | --- | --- | --- |
| [#1](https://github.com/tanabe-yudai/speclino/pull/1) | デモ1: テストが全部緑でも、仕様違反は反例つきで指摘される | `gate.py` の 1 か所で、必須ルールが無い結果を「通過」にした | `gate-decision#gate.decide_gate` が**違反**（反例つき） |
| [#2](https://github.com/tanabe-yudai/speclino/pull/2) | デモ3: 仕様を消して検査をすり抜けることはできない | リポジトリにある仕様の写し（`.speclino/specs/spec-ai-001.md`）から、必須の要求 `R-AI-07` の行を消した | `KNOWLEDGE-LOCK-001` が**未検証**（写しの改変を署名で検出） |
| [#3](https://github.com/tanabe-yudai/speclino/pull/3) | デモ4: 確認できなかったものは通さない | 振る舞いの変わらない `for` ループを入れた（解析できない形） | `gate-decision#gate.decide_gate` が**未検証** |

### 6-1. PR #1（デモ1）

1. https://github.com/tanabe-yudai/speclino/pull/1 を開きます
2. 「**Files changed**」タブで差分を見ます。`return _fail(...)` が `return _pass(t)` に変わっています
3. 「**Conversation**」タブの下の方にある、`speclino` のコメントを見ます

   ```
   ❌ SpecLino / gate: 失敗 — 違反 1・要確認 1・未検証 11
   ```

4. 「**Checks**」タブを開き、左の一覧の「**SpecLino / gate**」を押します

**確かめること**:

- 題に「違反 1 / 要確認 1 / 未検証 11 / 適合 135（ゲート: 失敗）」と出ます
- 要約に「必須ルール非成立: gate-decision#gate.decide_gate」と出ます
- 未検証・要確認の多くは助言（必須でない）の要求です。ゲートを止めているのは、この 1 件だけです
- 同じ PR の CI では、`test (backend)` は成功（緑）です。`self-check` は失敗しますが、これは「今のコードが自分の仕様に適合しているか」を
  確かめる別の検査が、デモの違反を正しく検出しているためです。単体テストは緑なのに、SpecLino だけが仕様違反を名指しします

### 6-2. PR #2（デモ3）

1. https://github.com/tanabe-yudai/speclino/pull/2 を開き、「**Files changed**」で 1 行の削除（`R-AI-07`）だけであることを確かめます
2. 「**Checks**」→「**SpecLino / gate**」を開きます

**確かめること**:

- 要約に「必須ルール非成立: KNOWLEDGE-LOCK-001」と出ます
- 検査は、リポジトリの写しではなく、SpecLino で承認済みの bundle で行います。写しの改変は、署名つきの `.speclino/lock.json` との照合で見つかります
- 要求を外せるのは、SpecLino の画面での改訂と、人の承認だけです

### 6-3. PR #3（デモ4）

1. https://github.com/tanabe-yudai/speclino/pull/3 を開き、「**Files changed**」で `for` ループが入っただけであることを確かめます
2. 「**Checks**」→「**SpecLino / gate**」を開きます

**確かめること**:

- 要約に「必須ルール非成立: gate-decision#gate.decide_gate」と「判定不能化 1」が出ます。main では適合だった要求が、未検証に変わっています
- 解析できない形のコードを「適合」とは言わず、未検証として扱います。必須の要求に未検証が残るので、ゲートは失敗します（フェイルクローズ）

## 7. SpecLino の検査詳細: 反例を見る（3 分）

SpecLino の画面に戻ります。

1. 上部の「**検査**」を押します。PR ごとの検査が並びます（「speclino #1」など）
2. 「speclino **#1**」の行を押します。直接開く場合は次の URL です
   https://speclino-web-6h5m3svkja-an.a.run.app/w/tanabe-yudai/runs/965d7530-b259-4c2b-9a09-29e960ceeed6
3. 画面上部で次を確かめます
   - ゲートの表示が「**失敗**」であること
   - 件数のタイル（違反・要確認・未検証・適合・確定済み・情報）
   - 「GitHub の PR」「Check」へのリンク
4. 「判定結果」の「**違反 1 件**」にある、`gate-decision#gate.decide_gate` のカードを読みます

**確かめること**:

- 「仕様の期待」と「実装」が並び、「実装」は「呼出し列: gate_pass」と表示されます
- 「**反例**」の枠（種別「記号的（静的解析による反例）」、経路 `p2_return`）に、条件と変数の割り当てが出ます
  - `before.triage.has_findings → true`
  - `before.triage.has_mandatory → false`

  これは「指摘はあるが必須ルールが 1 つも無い」という組合せです。この場合、図では失敗に進むはずなのに、実装は通過（`gate_pass`）を呼びます
- 「コード参照」に `src/speclino/conformance/gate.py` の行番号、「仕様参照」に図の該当行が出ます
- 「解析範囲」に、経路の数・ソルバーの上限・前提が書かれます。判定がどの範囲で成り立つかを明示しています
- 下のタブ「**レビュー（review.md）**」で、同じ内容を Markdown の報告書として読めます

5. 一覧に戻り、「speclino **#3**」（https://speclino-web-6h5m3svkja-an.a.run.app/w/tanabe-yudai/runs/6be75cfb-1c31-4a3c-bdfb-f9c133e4f0c3 ）を開きます。
   「未検証」の中の `gate-decision#gate.decide_gate` のカードを読みます

**確かめること**: 「解析の精度が incomplete のため判定しない（For は対応外の構文 …）」と、解析できなかった理由が具体的に出ます。

6. 「speclino **#2**」（https://speclino-web-6h5m3svkja-an.a.run.app/w/tanabe-yudai/runs/68c4de69-6c45-4740-96ab-62648b773a76 ）を開きます。
   「未検証」の中の `KNOWLEDGE-LOCK-001` のカードを読みます

**確かめること**: 「sync で書き出した知識が改変されているか欠けています」と出ます。

> 「要確認」のカードの下の「PR のコメントで確定するには」を開くと、承認者が GitHub の PR に書く `/speclino attest` のコマンドが出ます。
> 要確認を外せるのは、PR のコメントか PR の Approve を通した承認者の確定だけです。メンバーには確定のボタンは出ません。

1. ホームの「プロジェクトの健全性」で `speclino` を押します。直接開く場合は次の URL です
   https://speclino-web-6h5m3svkja-an.a.run.app/w/tanabe-yudai/p/tanabe-yudai/speclino
2. 「**概要**」タブで、次の 4 つを確かめます
   - 状態のパネル（要求と規約の判定の件数）
   - 「次にやること」
   - 「**要求**」の表
   - 「適用されている規約」

**確かめること**:

- 要求ごとに、仕様のファイル単位で、判定（違反・未検証・要確認・適合）と承認状態が並びます

## 9. 規約: チーム全体のルール（1 分）

1. 上部の「**規約**」を押します
2. 「ルール」の一覧で、各ルールの次の項目を確かめます
   - レベル（必須 / 助言）
   - 検査器（決定的な検査器、または AI 支援）
   - 結果（「N/M プロジェクトで未達」など）
3. 右の列の「改訂の履歴」と「監査ログ」を見ます

**確かめること**:

- 規約も、仕様と同じく改訂と承認で管理され、承認の記録が監査ログに残ります
- AI 支援の規約の判定は常に「要確認」で、人の確定を待ちます。AI に合否を決めさせません
- 「ルールを追加」「編集」はメンバーにも出ますが、「下書きに保存」は押さないでください（冒頭のお願い）

## 10. 観測: 知識が使われ、守られているか（2 分）

1. 上部の「**観測**」を押します
2. 次の 4 つのパネルを上から見ます
   - 「**リポジトリ**」: 検査できる要求の割合（形式化率）、判定できた割合、未検証の理由の内訳、最新の検査、検査に使った bundle が最新か
   - 「**取得の状況**」: 誰が（どのトークンが）、どの経路（リポジトリ同期 / エージェント）で、いつ知識を取得し、それが最新か
   - 「**規約ごとの推移**」: 規約ごとの判定の推移の棒グラフ
   - 「**AI 判定の状況**」: AI 支援の規約の指摘の有無、判定が割れた項目、記録の再利用率、人の確定

**確かめること**: 測っていない値は 0% や 100% ではなく「**未計測**」と表示されます。

## 11. 設定: エージェントへの配り方（1 分）

1. 上部の「**設定**」を押し、タブ「**エージェント接続**」を開きます
2. 次の 2 つの見出しを確かめます
   - 「エージェント接続（MCP / A2A）」: MCP の接続先と、A2A の Agent Card です
   - 「リポジトリ同期（speclino sync）」: リポジトリに書き出す手順です

**確かめること**:

- 承認済みの知識は、次の 3 つの経路で各自のコーディングエージェントに届きます
  - MCP（`knowledge_pull`・`spec_get` など）
  - A2A
  - CLI の `speclino sync`
- 書き出したファイルは、署名つきの `.speclino/lock.json` で手順 6-2 のように照合されます

## 付録 A. 手元の CLI でデモ1 を再現する（任意、約 10 分）

検査器は DB・GitHub App・GCP が無くても動きます。同じ入力からは同じ結果が出ることを、手元で確かめられます。
必要なもの: git、Python 3.12、[uv](https://docs.astral.sh/uv/)。

```sh
git clone https://github.com/tanabe-yudai/speclino.git
cd speclino
uv sync
uv run speclino check --repo . --base origin/main --head origin/demo/gate-passes-advisory-only \
  --specs-dir .speclino/specs --out build/review
```

検査は 1〜2 分で終わり、次の 5 行と成果物のファイル名が出ます。

```text
VERIFIED_IN_SCOPE: 134
VIOLATED: 1
UNKNOWN: 11
REVIEW: 1
gate: fail (advisory モード: 必須ルール 1 件が非成立（警告のみ）)
```

- 件数は GitHub の結果と少し違います。CLI では、サーバーで検査する lock の照合（`KNOWLEDGE-LOCK-001`）が入らないためです
- `build/review/review.md` を開くと、手順 7 と同じ反例が出ます（`before.triage.has_findings = True`、`before.triage.has_mandatory = False`）
- `--head` を次のブランチに替えると、デモ4 が再現できます
  - `origin/demo/loop-in-gate`: デモ4 で、同じ要求が UNKNOWN（未検証）になります
- 成果物は `build/review/` に出ます。`speclino replay build/review` で、凍結した入力から再評価して同じ結果になることを確かめられます

## 付録 B. うまくいかないとき

| 症状 | 対処 |
| --- | --- |
| ログイン後に「所属しているワークスペースがありません」 | アカウントを取り違えている可能性があります。提出フォームのメールアドレスでログインし直してください |
| 最初の表示が遅い | 初回はサーバーの起動とデータの取得に数秒かかります。再読み込みしてください |
| 「AI と作る」で「返答を得られませんでした」 | AI の 1 日の費用枠に達しています。手順 6 以降は AI なしで確かめられます |
| 本文を書き換えたまま画面を離れたい | 保存しなければ何も残りません。そのまま離れて構いません |
| 誤って「下書きを保存」を押した | 配信と検査には影響しません（承認されるまで、有効な改訂が使われ続けます）。そのままで構いません |
