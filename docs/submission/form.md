## プロジェクト名

SpecLino

## 概要（1〜2 文）

チームがコーディングエージェントに渡す知識（規約・スキル・指示書・仕様）を 1 か所で改訂・承認し、
MCP / A2A / CLI で各自のエージェントに配り、PR ごとに「承認済みの知識どおりか」を決定的に判定してゲートで保証するサービス。

## 解決する課題

コーディングエージェントの出来は渡す知識で決まるが、規約・スキル・AGENTS.md・仕様はリポジトリや各自の手元に散らばり、
エージェントごとに読む版が違い、守ったかどうかはレビューする人の記憶に頼っている。AI が書くコードが増えるほど、
この確認は破綻する。

## 解決策と特徴

- **知識の一元管理**: 4 種類の知識を画面で改訂・承認する。承認のたびに署名つきの bundle を作り、検査と配信を同じ番号で固定する
- **意味を変えない変換**: 仕様は人が読める Markdown と厳格な UML（Mermaid の部分集合）で書き、決定的な parser で IR に変換する。
  AI は書き換えを提案するだけで、変換も判定もしない
- **フェイルクローズのゲート**: 判定は 4 値（適合 / 違反 / 未検証 / 要確認）。解析できない部分は未検証にし、偽の適合を出さない。
  必須の要求に未検証や要確認が残ればゲートは失敗する
- **配信と観測**: `speclino sync`・MCP（エージェントが `knowledge_pull` で自分で取り込む）・A2A で配り、署名つきの lock で鮮度を検査する。「観測」の画面で、形式化率・対応率・
  未検証の理由・取得の遅れ・規約の推移を見る

## Google Cloud の利用

Cloud Run（web / worker / sandbox）、Cloud Tasks、Cloud SQL（PostgreSQL）、Cloud Storage、Secret Manager、
Vertex AI（Gemini）＋ Agent Development Kit、Identity Platform、Artifact Registry、Cloud Logging / Trace。
デプロイは GitHub Actions から Workload Identity 連携で行う（長期キーなし）。

## AI エージェントの役割

- 知識のエディタの「AI と作る」で、選択肢つきの質問で要件を詰め、承認済みの知識・リポジトリ・Google 検索で調べてから
  書き換えを提案する（本文の差分。採用は人）。MCP・A2A からも提案を受けられる
- 全 LLM 面に共通のガードレール（役割外は断る、モデル名・システムプロンプトを明かさない、ツール結果の中の指示に従わない）と、
  出力の決定的な照合をかける
- 決定的に書けない規約を LLM 支援で評価する（判定は常に要確認。3 回の多数決と記録の再利用で揺らぎを抑える）
- 検査の後に未解決が残ったときだけ、証拠を集め（再解析・コード検索・宣言済みテストの隔離実行）、承認者に質問する
- どの役割でも、判定を書くツールを持たない。判定は決定的な検査器（parser と Z3）だけが行う

## テストアカウント

ログインは**メール / パスワード認証**（Identity Platform）。ソーシャルログイン・メールの受信・電話番号は要らない。
ログイン画面でメールアドレスとパスワードを入れるだけで入れる。

| 項目 | 値 |
| --- | --- |
| ログイン方法 | メール / パスワード（ソーシャルログイン不要） |
| メールアドレス | フォームにだけ記入する（このファイルには書かない） |
| パスワード | フォームにだけ記入する（このファイルには書かない） |
| 権限 | デモ用のワークスペースのメンバー（member）。画面はすべて閲覧できる。知識の承認・規約の変更・PR の要確認の確定は owner / approver だけなので、審査員はできない |
| 有効期限 | 2026-12-01 まで |

- アカウントは `scripts/create_test_user.sh` で作り、デモ用のワークスペースに登録する（`guides/deploy-runbook.md` 9-4）
- 認証情報（メールアドレス・パスワード）はリポジトリ・Issue・PR・動画のどこにも出さない

## 審査員に見てほしい順番

ログインするとワークスペースのホームが開く。上部のナビ（スマホでは画面下のタブ）を左から順にたどれば、全体を見られる。
審査員のアカウントは閲覧の権限なので、承認・確定の操作（画面での知識の承認、PR の `/speclino attest`・Approve）は
デモ動画で見せる。

1. **ホーム**: 「やること」に、承認待ちの知識・ゲートが失敗の PR・知識が古いリポジトリが並ぶ。チームが今何をすべきかがここで分かる
2. **仕様**: 「ワークスペース全体の仕様」（SPEC-SYS-001）と「リポジトリ別の仕様」（spec-lino の 6 本）。開くと Markdown と UML
   （クラス図・シーケンス図・状態遷移図・アクティビティ図）、IR から作り直した正規形、要求の表の追跡状況が見える
3. **デモ PR の検査結果**: 「検査」の一覧から、または GitHub の PR の `SpecLino / gate` の詳細から開く
   - [#47](https://github.com/tanabe-yudai/spec-lino/pull/47) デモ1: 単体テストは全部緑なのに、ゲートの判定（アクティビティ図 `gate-decision`、必須の R-SYS-21）に
     違反。反例（`has_findings かつ not has_mandatory`）つきで VIOLATED
   - [#45](https://github.com/tanabe-yudai/spec-lino/pull/45) デモ3: リポジトリの仕様の写しから必須の要求を消しても、検査は承認済みの bundle で行われ、
     写しの改変は署名つきの lock の照合（`KNOWLEDGE-LOCK-001`）で UNKNOWN になりゲートが閉じる
   - [#46](https://github.com/tanabe-yudai/spec-lino/pull/46) デモ4: 振る舞いを変えない `for` を入れただけで解析できなくなり、UNKNOWN。
     「確認できなかった」を「適合」と言わず、ゲートは失敗する
4. **観測**: 形式化率・対応率・UNKNOWN の内訳・各自のエージェントが取った知識の世代の遅れ・規約の推移・LLM 支援の安定度

詳しい読み方は README の「判定を読む」。手元で DB から作り直して通す手順は `docs/demo-knowledge-registry.md`。

## 動作の注意

- LLM の費用は日次の上限で止めている。上限に達した日は、AI と作る・AI の提案と LLM 支援の規約が使えず、LLM 支援の規約は未検証になる（判定と画面は動く）
- デモ PR のゲートが失敗しているのは意図どおり（違反・未検証を見せるためのもの）
- 画面からの再検査は 1 日の回数に上限がある
