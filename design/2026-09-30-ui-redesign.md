# UI の刷新: デザインの土台・プロジェクト画面（S45）・チーム規約画面（S43）・ランディングページ（2026-09-30）

ブレインストーミング（2026-09-29〜30、ブラウザのモックで確認）で合意した設計。実装計画は別文書。

## 1. 目的と条件

- **目的**: 審査で伝わること（デプロイ URL と 3 分の動画で「何ができて、なぜ新しいか」が掴める）と、
  そのまま公開できる製品であることを同じ重さで満たす
- **質感**: 管理画面らしさではなく、モダンで未来感のあるアプリ。方向は「光の空間」（明るい地に柔らかな
  光のグラデーション、浮いたパネル）。オーロラ系の強い発光は使わない（うるさい）
- **構成**: 上部のピルでワークスペース / プロジェクトを切り替え、プロジェクトは 1 ページに集約
  （状態 → 要求 → 規約 → 検査履歴）。右に「次にやること」
- **原則を崩さない**: 判定は検査器だけが行い、4 値（適合 / 違反 / 未検証 / 要確認）を正直に出す。
  「次にやること」は検査結果から決まった規則で並べ、LLM で作らない
- **個人の環境の値を画面・文書に書かない**（例は `example-org/...` や置き換え記号）
- 招待制のまま（新規登録の入口は置かない）

## 2. 進め方（分割と順序）

ユーザー判断で「土台を先に全部作る」順にする。各段は独立に計画・実装・リリースできる。

1. **土台**: デザイントークン、shadcn/ui の導入、アプリの外枠（上部のピル・テーマ切り替え・アカウント）、
   既存の全画面（ログイン・ホーム・検査の詳細・リポジトリ・MCP トークン・コールバック）の作り直し
2. **S45 プロジェクト画面**（新しい API を含む）
3. **ランディングページ**
4. **S43 チーム規約画面**（新しい API を含む）

AI とのチャットは今回作らない（別ストーリー。最初の版は「検査結果の根拠つきの説明（読み取り専用）」）。
今回は「次にやること」のカードに入口の場所だけ用意する。

### 3.2 技術

- **shadcn/ui ＋ Tailwind CSS v4** を導入する（Vite の公式手順: `tailwindcss` と `@tailwindcss/vite`、
  `vite.config.ts` に `@` の別名、`shadcn init`）。部品のソースはリポジトリに取り込まれ、3.1 のトークンを
  shadcn の CSS 変数（`--background` `--card` `--primary` など）に当てはめる。今の手書きの CSS
  （`App.css`・`index.css`）は作り直しに合わせて置き換え、最後に消す
- 使う部品: Button、Card、Badge、Dialog（確認）、DropdownMenu（ピルの切り替え・アカウント）、
  Command（⌘K のパレット）、Tooltip、Tabs、Sonner（トースト）、Skeleton（読み込み中）
- **ライト / ダーク**: `<html>` の `.dark` クラスで切り替える（Tailwind の `@custom-variant dark`）。
  既定は OS の設定、ヘッダーのボタンで手動に切り替え、選んだ値は `localStorage` に保存（読めなければ
  OS に従う）。初回の描画でちらつかないよう、`index.html` で先に `.dark` を付ける
- 型は `web/src/types/`、API 呼び出しは `web/src/api/`、判定の並べ替えや「次にやること」の規則は
  `web/src/services/`（画面に書かない）。この規約は今までどおり
- 動きは CSS のトランジションと Tailwind のアニメーションで出す（ホバーの浮き、脈打つ点、ランディング
  ページの判定の確定）。`prefers-reduced-motion` では止める

## 5. S45 プロジェクト画面

### 5.1 並び

1. **状態**: 健康状態のリング（適合の割合）、4 値の件数、未承認の要求の件数、最新の検査（PR 番号・head・時刻・
   ゲート）と詳細へのリンク
2. **要求**: 仕様ファイルごとにまとめる。各行に ID、題、承認の状態（承認済み / 未承認 / 承認切れ）、宣言された
   テストの数、最新の判定。絞り込み（すべて / 違反 / 未検証 / 要確認 / 未承認）。違反・未検証の行は開くと
   反例・経路・仕様の該当行（GitHub へのリンク）・検査の詳細へのリンク
3. **適用されている規約**: チームの改訂番号とプロジェクト固有の規約。各規約に必須 / 助言、検査器の有無、成否
4. **検査履歴**: その project の run（新しい順。PR・head・ゲート・時刻）

右に固定で「次にやること」（5.3）。

### 5.2 API

`GET /api/workspaces/{slug}/projects/{project_id}/overview`（メンバーだけ。それ以外は 404）。
その project の**最新の完了した検査**（`exec_state` が completed または awaiting_answer）の成果物から組み立てる:

- 要求: 成果物の Spec IR（`spec-ir.json`）のルール（ID・題・振る舞い・承認の有無・`tests` の数・仕様ファイルと行）
  × findings の判定。承認切れ = 承認の内容ハッシュ不一致の finding がある要求
- 規約: manifest のチーム改訂番号 ＋ 規約の findings（`<rule>:<path>`）をルールごとに集計
- 検査履歴: その project の run 一覧（上限 20）
- 検査がまだ無ければ `{"status": "not_checked"}` を返し、画面は「まだ検査されていない」とだけ出す（推測で埋めない）

組み立ては `services/`（新規 `project_overview.py`）に置き、ルートは呼ぶだけ。成果物の読み出しは既存の blob store。
プロジェクトの一覧（ホーム用）も同じサービスで、各 project の最新の検査の件数だけを返す
`GET /api/workspaces/{slug}/projects`。

### 5.3 「次にやること」の規則（`web/src/services/nextActions.ts`）

検査結果から次の順で最大 5 件を並べる（LLM は使わない）:

1. 違反の要求（反例を見る → 検査の詳細）
2. 承認切れの要求（仕様の PR で再承認）
3. 要確認の要求（人の確認が要る質問）
4. 未検証の要求（エージェントの調査の結果を見る）
5. 未承認の要求（仕様の PR で承認）

何も無ければ「すべて確認済み」。カードの下に「この件について質問する」の場所（今回は無効表示）。

## 6. S43 チーム規約画面

- **上部の帯**: 下書きがあるときだけ。変更の件数・作成者・時刻、「差分を見る」、「承認して有効にする」
  （owner / approver にだけ表示。API も拒否する）
- **中央**: 有効な改訂のルールの一覧。各ルールに ID・題・必須 / 助言・検査器の有無・直近の成否・適用範囲・
  例外の可否。行を開くと編集のフォーム（題・本文・レベル・適用範囲・例外の可否・検査器の選択）→ 保存で下書きに入る。
  下書きで変わった箇所は差分で見せる（例: 助言 → 必須）。ルールの追加もここから
- **右**: 改訂の履歴、監査ログ（誰が・いつ・何を。承認の拒否も含む）
- **決めごと**: 下書きは同時に 1 つ。下書きはメンバーなら誰でも作れる。承認は owner / approver で、作成者本人の
  承認も認め、監査に残す。承認すると新しい有効な改訂になり、以後の検査の manifest にその番号が出る
- **API**（新規、`/api/workspaces/{slug}/policies` 配下）: 有効な改訂と下書きの取得、下書きの作成・更新、承認、
  改訂の履歴、監査ログ、検査器の一覧。判断は既存の `services/policy_governance.py`（排他・承認者の検証・監査）を使う
- **直近の成否**: そのワークスペースの各 project の最新の検査の規約 findings から集計（5.2 と同じ出どころ）
- **本番の初期化**: 本番にはチーム規約の改訂がまだ無いので、切り替え時に admin Job の `policy seed` で初期改訂を入れる

## 7. ランディングページ

- **ヘッダー**（上部に固定）: ロゴ、「はじめ方」「原則」へのページ内リンク、テーマ切り替え、**ログイン（ここだけ）**
- **ヒーロー**: 「仕様はいつもの場所に。検証はエージェントと。」、承認した仕様と実装の意味の差を検査器が反例つきで
  示す、という一文。ボタンは「使い方を見る ↓」だけ。右に PR の検査の見本（判定が順に確定するアニメーション。
  実データではない）
- **はじめ方（01〜04）**: 左に説明、右に実物。01 リポジトリをつなぐ（リポジトリの画面）、02 仕様を書いて PR で承認
  （仕様の Markdown と承認のコメント）、03 エディタから使う（`claude mcp add` と MCP の応答）、04 PR で確かめる
  （健康状態のリングと「次にやること」）。実物は画像ではなく、新しい UI の部品を見本データで描く
- **原則**: 判定は 4 値のまま / AI は判定しない / 記録が残る
- **末尾**: 「SpecLino は現在、招待制で提供しています。」（ボタンは置かない）
- ページのタイトルと OGP を設定する。「デモ」という言葉は使わない（サービスとして書く）

## 8. テストと確認

- API（overview・projects・policies）は統合テスト: 非メンバー 404、検査が無いとき not_checked、要求 × 判定の組み立て、
  承認切れの判定、規約の集計、下書き → 承認の権限（approver でない人は 403 相当で拒否し監査に残る）
- `services/nextActions.ts` などの画面側の規則は単体テスト（web にテストの仕組みが無ければ導入する）
- 画面は web の lint・型・ビルドに加えて、主要な画面をライト / ダークの両方でブラウザで確かめる
- 既存の検査（`make check`・`make eval`）は変えない

## 9. 非目標

- AI とのチャット（別ストーリー）
- 仕様の Markdown 本文を画面に描くこと（要求は Spec IR から構造化して見せ、本文は GitHub の該当行へ）
- 新規登録・外部チーム向けの導入案内（招待制のまま）
- 規約の承認を UI 以外で行う経路の追加（CLI の既存経路はそのまま）
