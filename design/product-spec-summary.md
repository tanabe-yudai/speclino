# SpecLino 製品仕様の要約（暫定仕様書 v0.6 より）

正本は `docs/SpecLino_暫定仕様書_v0.6.md`（Git 管理外）。本書は、実装時に参照する要件だけを抜き出した要約。意味検証コアの詳細は `2026-09-22-semantic-conformance-poc-v0.1.md`、ハッカソン向けの取捨選択は `2026-09-22-hackathon-plan.md` を参照。

## 目的

仕様・コード・チーム規約を機械で照合できる表現へ変換し、仕様どおりの実装であることと合意した開発ルールに従うことを、追跡可能な証拠に基づいて確認する。人の確認対象を「判断が必要な差分」へ絞る。

| 検証関係 | 確認内容 |
|---|---|
| 仕様と実装 | 条件、状態遷移、副作用、応答が一致しているか |
| 規約と仕様 | 書式、必須項目、用語、API 設計が共通ルールに従うか |
| 規約と実装・設定 | コード、Makefile、CI/CD 定義が共通ルールに従うか |

## 設計原則（実装で守るもの）

- **判定はエンジン、エージェントは証拠収集**（9章）。エージェントは根拠不足を文章で埋めて通過させない。最終判定は決定的な検証エンジンが行う。
- **ツール権限は実行前に検査し、監査記録を残す**（FR 014 / AC-012）。直接のコード書込み・マージ・デプロイ・本番アクセスは許可しない。モデルへ提示した文書やリポジトリ内の指示から権限を変更できない。
- **実行上限**（9章）: 1 実行につきツール呼出し 20 回、経過時間 10 分を初期上限。到達理由を記録し、未検証項目を返す。
- **版と証拠の固定**（FR 016）: 実行開始時にコード・仕様・規約・例外・スキル・検証器・モデル設定の版を固定。保存した IR・証拠からの再評価と、LLM を再実行する再抽出を区別する。
- **古い実行の不採用**（FR 017 / AC-011）: PR 更新後の古い実行は履歴に残し、新しいコミットの結果へ上書きしない。
- **ルール削除で違反を暗黙に解消しない**（FR 017 / AC-010）: 規約・仕様・コードが同じ PR で変わった場合、規約と検証条件の変更承認を独立して確認する。
- **原文を失う不可逆な置換をしない**（5章）。IR は原文 ID・版・内容ハッシュへの参照を持つ。
- **名称が似ているだけで同一処理と確定しない**（FR 010）。対応が一意でなければ複数候補を保持し、人へ確認する。
- **保証範囲の明示**（8章）: 出力には対象コミット、仕様版、規約版、検証器版、前提、対象範囲、未確認範囲を必ず付ける。テスト成功だけで全経路への適合とはしない。
- **実行状態と判定の分離**（8章）: 待機・実行中・回答待ち・完了・失敗・取消は実行状態であり、適合性の判定とは別に保持する。空の検証集合・取得失敗・解析器障害を適合として扱わない。
- **正本は外部**（2章、16章）: 仕様の編集・レビュー・承認は GitHub 等で完結させ、本サービスに独立した仕様編集・承認機能を設けない。Web は差異と確認待ちに絞る（FR 019 / AC-027）。

## ゲート（FR 013）

必須ルールの違反は失敗。通過は、必須の適用対象がすべて適合するか、有効な例外で免除された場合。例外付き通過は通常の適合と区別する。助言ルールは結果を残すが単独ではマージを止めない。接続先（GitHub Checks）が保留を表現できない場合は非成功へ写像し、必要なチェックが存在しないときも通過させないようリポジトリの保護設定を確認する。

> ハッカソン版の補足: 仕様書 8 章の「確認不能」はゲート上はフェイルクローズ（非成功）として扱う。Finding の verdict は正直に UNKNOWN / REVIEW を保つ（`2026-09-22-hackathon-plan.md` 判定モデル）。

## 規約パッケージ（3章、7章）

規約は版付きパッケージとして Git 管理する。各ルールは識別・適用範囲・本文・検証方法・判定と運用（必須か助言か、必要証拠、例外の可否）を持つ。例外は規約 ID・対象・理由・承認者・期限・代替策を必須とし、免除として別記する（期限切れは無効、AC-009）。

規約の実装例: `API-ERR-001`（エラー形式）、`API-AUTH-001`（認証方式）、`MAKE-001`（標準ターゲット。存在だけで実処理の成立とはしない、AC-004）、`DEPLOY-001`（本番承認）、`DEPLOY-002`（手順と復旧）。Makefile・CI 定義は読み取りで検査し、未信頼の Makefile をホスト上で評価しない。

## エージェントのツール（FR 014）

`repo.search`、`graph.query`、`policy.check`、`test.run`、`docs.lookup`、`human.ask` を個別許可。権限検査はツール実行前。外部照会は許可した宛先とデータ範囲に限定。質問（FR 015）は対象版・原文・候補解釈・必要な回答・正本側レビューへのリンクを持ち、質問中に対象が変われば再確認する。

## 外部インターフェース案（11章、20章）

`POST /review-runs`、`GET /review-runs/{id}`、`GET /review-runs/{id}/events`、`GET /projects/{id}/rules`、`POST /questions/{id}/answers`、`POST /policy-exceptions`、`POST /findings/{id}/feedback`。MCP 操作: `context.get`、`spec.propose`、`approval.prepare`、`approval.get`、`verification.start / get`。PR チェックには仕様整合性・規約適合性・未確認項目・例外・検証範囲を表示し、指摘には仕様 ID・規約 ID・原文位置・対象コード・判定理由・証拠・修正の方向を添付する（FR 018）。

## 非機能要件（12章）

| ID | 要件 |
|---|---|
| NFR-001 | すべての判定から原文、入力版、証拠、解析範囲へ到達できる |
| NFR-002 | 同じ固定 IR・規則・証拠の再評価は同じ判定となる。LLM 再抽出の一致は保証しない |
| NFR-003 | プロジェクト間のデータと権限を分離し、秘密情報をモデル入力・ログへ送らない |
| NFR-004 | 未信頼コード・Makefile・検証器は、資源制限と外部通信制限のある環境で扱う |
| NFR-005 | 承認、権限変更、例外、拒否、判定変更を監査履歴として保存する |
| NFR-006 | 標準サンプルで初回結果 5 分以内を暫定目標とし、時間と費用を測定する |
| NFR-007 | 取得失敗や実行障害を適合から区別し、再試行・取消・再開を管理する |
| NFR-008 | 解析器・モデル・仕様保存先・コード接続先をアダプタ境界で交換可能にする |

## MVP の段階（13章）

A 規約と仕様（スキル・MCP・規約・外部承認の参照）→ B 設定検査（API 応答スキーマ、Makefile、CI/CD）→ C 振る舞い検証（条件、HTTP 応答、状態遷移、禁止副作用）→ D 統合体験（PR 出力、調査と質問、再検証）。最初の実証は単一 GitHub リポジトリ、Python 3.12 + FastAPI。

## 名称

SpecLino（スペクリノ）。Spec（仕様）と Link（つなぐ）からの造語。「仕様とコードをつなぎ、合意を確かめる。」
