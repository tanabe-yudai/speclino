# A2A で仕様を議論する SpecLino エージェント（2026-10-04）

ブレインストーミング（2026-10-04）で合意した設計。実装計画は別文書。

## 1. 目的

ユーザーが使うエージェント（Claude Code など）と SpecLino 側のエージェントが、仕様について往復で議論できるようにする。
次の 4 つを同じ重さの目標にする。

- (a) 仕様を書く段階の相談: 下書きのあいまいさ・既存の要求や規約とのぶつかり・Spec IR の候補を返し、聞き返しながら詰める
- (b) 実装中の相談: 「この要求の意味は」「この変更で R-xxx は大丈夫か」に、Spec IR と判定を根拠に答え、必要なら検査器にかける
- (c) 検査の後の聞き取り: 「要確認」の点について、相手のエージェントから根拠や意図を集める
- (d) 審査で「エージェント同士が仕様を議論している」ことを見せられる

## 2. 役割の分け方（A2A と MCP）

- **A2A**: SpecLino エージェントとの**会話**（聞き返し・論点を詰める往復）
- **MCP**: **関数**としての呼び出し（`context_get`・`verification_start`・`verification_get` のように 1 回で結果が返るもの）

Claude Code は A2A を直接は話せないが、MCP 経由で A2A エージェントと話す仲介（コミュニティ製の A2A MCP サーバーやプラグイン）がある。
SpecLino は標準の A2A サーバーを出し、A2A 対応のエージェントと、仲介を入れた Claude Code の両方から使えるようにする。

## 3. SpecLino エージェントがしてよいこと・しないこと

**してよいこと**（Agent Card のスキル）

1. 仕様のレビュー（`spec_review`）
2. 要求の相談（`requirement_consult`）
3. 検査の後の聞き取り（`run_clarification`）

**しないこと**

- 判定しない。違反・適合を決めるのは検査器だけで、会話で判定を変えない
- 承認しない。仕様・規約の承認、例外の登録は人の操作（PR のコメント・画面）だけ
- 人の代わりに答えない。「要確認」への正式な回答（`/speclino answer`）は人だけ。エージェントの答えは補足
- リポジトリに書き込まない。仕様や IR の修正は提案として返すだけ
- トークンのワークスペースの外を話さない

## 4. 構成

方式: A2A の公式 Python SDK（`a2a-sdk`）でサーバーを立て、中で ADK と Gemini のエージェントを動かす。
ADK の付属の A2A 化（`to_a2a`）は使わない。認証・会話の記録・入力待ちの制御を自前で持ち、Cloud Run の複数のインスタンスで往復を落とさないため。

- **A2A の入口**（web サービスに追加）
  - Agent Card: `/.well-known/agent-card.json`（スキル 3 つ、認証の方式）
  - エンドポイント: `/a2a`（JSON-RPC）
  - 認証: MCP と同じワークスペースのトークン（`slmcp_`）を Bearer で受ける。トークンからワークスペースを決める
- **議論役**（`src/speclino/agent/consultant/`、新規）: ADK と Gemini のエージェント。スキルごとに指示を切り替える。ツールはすべて既存の門番（`agent/gateway.py`）を通し、監査に残す
  - 仕様の下書きの検証（`spec_extractor` と `spec_validator` と同じ処理。書き込みなし）
  - Spec IR・最新の判定・規約を読む（`services/project_overview.py`・`services/mcp_context.py` の読み出し）
  - 指定したコミットでの検査の起動と結果の取得（MCP の `verification_*` と同じサービスの関数）
  - 補足の記録（6 章）
- **会話の記録**: A2A のタスクとメッセージを DB に置く（追加のマイグレーション）。インスタンスをまたいでも往復が続く
- **費用**: 既存の日次の費用枠。呼び出しの前に最悪の場合の費用が残りの枠に収まるかを確かめる（S46 の `CostGuard.can_afford` と同じ）。1 タスクの往復の回数と合計トークンにも上限

### 流れ（例: 仕様のレビュー）

1. 相手が仕様の下書きを送る（`message/send`、スキル `spec_review`）
2. 議論役が検証ツールで候補と診断を作り、あいまいな箇所を質問にまとめる
3. タスクを「入力待ち」（`input-required`）にして質問を返す
4. 相手が同じタスクで答えると再開し、指摘と修正案（Markdown の差分）を返す
5. タスクは「完了」。取り込みと承認は人が PR で行う

## 5. スキルの入出力

### `spec_review`

- 入力: 仕様の Markdown（テキストまたは Markdown のファイル）、リポジトリ（`owner/name`）、behavior（任意。無ければ既存の IR から推定）
- 途中: IR にできない点やあいまいな点があれば、質問の一覧を付けて入力待ち
- 出力（成果物）: Spec IR の候補、診断（W_AMBIGUOUS / W_UNEXTRACTED / E_REF_UNDEFINED など）、既存の要求や規約とのぶつかり、Markdown への修正案（差分）、要約。「取り込みと承認は PR で人が行う」と毎回明記する

### `requirement_consult`

- 入力: 質問の文、リポジトリ、要求 ID（任意）、検査したいコミット（任意）
- 途中: コミットがあれば検査を起動し、「作業中」を流しながら結果を待つ
- 出力: 説明の文（根拠として仕様のファイルと行・Spec IR の要求・判定の ID を必ず添える）。検査した場合は検査器の判定と反例をそのまま返す。説明の中で「違反しない」と言い切らず、判定は検査器の結果として示す

### `run_clarification`

- 入力: 検査（run）の ID
- 途中: その検査の「要確認」の点を質問として返し入力待ち。答えを補足として記録し、次の質問へ
- 出力: 記録した補足の一覧
- SpecLino から相手のエージェントに話しかける形は作らない（相手に A2A サーバーが要るため）。相手から聞きに来たときに質問を出す

## 6. 補足（エージェントからの補足）

- 新しい表 `agent_supplements`（追加のマイグレーション）: 検査・質問または要求・内容・どのトークン（どのエージェント）から来たか・時刻
- 正式な回答ではない。「要確認」を解消するのは人の `/speclino answer` だけで、判定にもゲートにも効かない
- 画面: 検査の詳細の要確認の点の下に「エージェントからの補足（正式な回答ではありません）」として出す

## 7. 失敗したときの扱い

- 認証できない・ワークスペースの外: A2A の決まりに沿ったエラー。存在は漏らさない
- Gemini の失敗・費用枠の超過: タスクを「失敗」にし、理由を返す。途中までの結果を判定のように見せない
- 検査が時間内に終わらない: 「作業中」のまま検査の ID を返す（MCP の `verification_get` か同じタスクへの問い合わせで続きを取れる）
- 入力が大きすぎる: 仕様は 3 万文字まで（S46 と同じ）。超えたら呼ぶ前に断る
- 門番が拒否した: 監査に残し、その旨を返して続ける

## 8. テストと確認

- A2A の層（Agent Card・認証・タスクの往復・入力待ちからの再開・DB への保存）: 公式 SDK の上の統合テスト。Gemini は台本の偽物
- 議論役の権限: 門番のテストで固定（使えないツールを呼べない、補足が判定・ゲートに効かない）
- エンドツーエンド: 公式 SDK のクライアントから 3 つのスキルを順に呼ぶ
- 本番: デプロイ後、外から A2A のクライアントで 1 往復させて確かめる
- `make check`・`make eval` を変えない。`conformance/`・`analysis/` は LLM・adapters に依存しないまま

## 9. 非目標

- SpecLino から相手のエージェントへの呼びかけ（相手側の A2A サーバーが要る）
- 会話による承認・判定の変更
- A2A の会話の一覧を見る画面（補足の表示だけ）
- A2A の gRPC・REST のトランスポート（JSON-RPC だけ）
