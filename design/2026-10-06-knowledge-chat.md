# 対話による知識の作成（2026-10-06、S73）

仕様・スキル・指示書・規約を、画面の上で AI と会話しながら下書きできるようにする。
`2026-10-05-team-knowledge-registry.md` の原則（AI は変換も判定もしない、保存と承認は人）を変えない。

## 1. 目的

- 「社内の CLI ツール `foo` の使い方をスキルにしたい」「注文のキャンセルの仕様を書きたい」と話しかけて、
  下書きを作り、直していける
- 自分の会話は残り、続きから再開できる。**他人の会話は見えない**
- 変更ごとに、会話の要約（何を・なぜ・見送ったこと）を改訂の説明として残し、承認者が経緯を読める

## 2. 決定事項

| # | 決定 | 理由 |
| --- | --- | --- |
| C1 | 対象は仕様・スキル・指示書・規約の 4 種類 | ユーザー判断（2026-10-06） |
| C2 | 会話はユーザーごとに DB に残し、**SpecLino の画面と API では本人だけ**が読み書き・削除できる（owner / approver にも見せない）。秘密の境界はアプリの認可。会話は Vertex AI（Gemini）に送られ、DB の運用者・バックアップからは技術的に読めることを画面で告知する | ユーザー判断。運用者まで暗号で遮る要件にするとサーバで AI を動かせないため、境界をアプリに置く |
| C3 | 下書きの保存時に、AI が会話の要約を作り、**本人が確認・編集してから**改訂の `note` に入れる。承認者は要約だけを読む | ユーザー判断。本人が確かめてから出すので、見せたくない内容が漏れない |
| C4 | AI の返答は「説明の文」と「下書きの提案」。提案できる欄は種類ごとの**許可リスト**に限る: 仕様は `markdown`、スキルは `skill_md` と付属ファイルの本文、指示書は `body`、規約はルールの定義（id・title・text・level・tier・verifier・params・applies_to）。名前・`scope`・`target`・`domain`・`legacy_ir`・`compiled`・承認の情報は応答の型に含めない。提案は元の本文のハッシュに結び付け、本文が変わった後の古い提案は反映できない。「エディタに反映」で**編集欄にだけ**入る。保存・承認は人 | AI を判定と保存の経路に入れない（D5 の延長）。規約のルールの定義はゲートを左右するが、承認者が必ず見る下書きであり、承認時の検証も独立に再実行する |
| C5 | 提案は返す前にサーバで検証し、`raw_proposal`（許可リストの欄だけの文字列・JSON）と `diagnostics` で返す（型に合わない提案も返すが、`ArtifactContent` としては返さない）。仕様は `compile_spec`、スキル・指示書は `domain/knowledge.py` の型、規約は `PolicyRule` と検査器の一覧。この検証は診断にすぎず、保存時・承認時の検証は既存どおり独立に行う | 「直していける」ことを優先し、通らないことは隠さない |
| C6 | AI はツールを持たず、DB に書かない。会話・本文・ワークスペースの知識の名前は信頼しないデータとして区切ってプロンプトに入れる | プロンプトインジェクションの影響を、提案の文面に閉じ込める |
| C7 | 費用は既存の日次の枠で、呼ぶ前に最悪の額を予約し、どの終わり方でも精算する（S67 の `SuggestBudget` を使い回す）。加えて**ユーザーごと**の上限（1 日 50 発言・1 日の費用は全体枠の 20%）と**ワークスペースごと**の上限（全体枠の 50%）を原子的に数える。1 回の呼び出しの入力は 64KB（会話は直近から 48KB まで、残りは含めない）、出力は 4,096 トークンに固定。予約は入力のバイト数を上界とする | 1 人で共有の枠を使い切って、判定や他の人の利用を止めないため |
| C8 | 発言には利用者が生成した冪等キーを付ける。発言の処理は「保留の発言を作る（短いトランザクション）→ LLM（ロックを持たない）→ 持ち主と版を確かめて確定」の順。会話が途中で消えていたら応答を捨て、行を復活させない。同じ冪等キーの再送は LLM を呼ばずに前の結果を返す | 二重送信・複数のタブ・削除との競合で、取りこぼしや二重の課金を起こさないため |
| C9 | 秘密の扱い: 監査は会話専用の型つきの関数（`chat_id`・件数・成否だけ）で残す。会話の API のエラーは固定のコードだけを返し、入力・LLM の生の応答・プロンプト・事業者の例外を応答にもログにも出さない。ログ・トレースに本文を出さない（テストで固定） | 「本人だけ」をアプリの外側の経路から崩さないため |

## 3. データ

新しい表 `knowledge_chats`（マイグレーション 0012、追加のみ）。

| 列 | 内容 |
| --- | --- |
| `id` | UUID |
| `workspace` | ワークスペース |
| `owner_uid` | 会話の持ち主（SpecLino の uid） |
| `kind` | 専用の型 `knowledge_chat_kind`（spec / skill / instructions / policy）。既存の `artifact_kind` は広げない |
| `artifact_id` | 対象の知識（新規作成中は NULL、保存後に結び付ける）。NULL 可の外部キー（artifact が消えたら NULL）。`kind=policy` は常に NULL（CHECK 制約）で、チーム規約を指す |
| `title` | 一覧の表示用（最初の発言から作る、本人が変えられる、120 文字まで） |
| `messages` | JSONB。`[{id, role: user|assistant, text, proposal?: {...}, idempotency_key?, status: pending|done|failed, created_at}]`。1 会話あたり 200 件・合計 512KB まで（アプリで検査。超えたら新しい会話を促す） |
| `version` | 楽観的な排他のための連番 |
| `created_at` / `updated_at` | サーバの既定値。更新はリポジトリが進める |

- マイグレーション 0012（`down_revision = "0011"`、追加のみ）。`workspace` は `teams` への外部キー。一覧の索引 `(workspace, owner_uid, updated_at)`
- **メンバーをワークスペースから外したら、その人の会話を消す**（本人にも owner にも読めないデータを残さない）。ワークスペースの削除でも消える
- artifact への結び付けは、サービスで会話の持ち主・ワークスペース・種類と artifact のワークスペース・種類が一致することを確かめる
- ORM の `KnowledgeChatRecord` と、モデルのテスト（列・型・制約）を足す

- 読み・書き・削除のすべての問い合わせを `workspace` と `owner_uid` で絞る。他人の会話の ID を指定されたら 404
- 監査には「会話を作った・消した」と件数だけを残し、本文は残さない（C9）
- 改訂の `note`: 知識（仕様・スキル・指示書）の作成・下書きの更新の API・サービス・リポジトリに `note`（500 文字まで、下書きの版の照合の対象）を足し、改訂の画面に表示する。規約は既存の `note` を使う。要約から入れた場合は `note_source: "chat_summary"` を監査に残すが、これは**本人の申告**であってサーバが由来を証明するものではない。要約を `note` に入れて保存した時点で、その内容は本人が共有したものとして扱う

## 4. API（すべてワークスペースのメンバーだけ、他のワークスペースは 404）

| メソッド | パス | 内容 |
| --- | --- | --- |
| GET | `/api/workspaces/{slug}/knowledge/chats?kind=&artifact_id=` | 自分の会話の一覧 |
| POST | `/api/workspaces/{slug}/knowledge/chats` | 会話を作る（kind、artifact_id 任意） |
| GET / DELETE | `/api/workspaces/{slug}/knowledge/chats/{id}` | 自分の会話を読む・消す |
| PATCH | `/api/workspaces/{slug}/knowledge/chats/{id}` | 名前の変更・artifact への結び付け（`expected_version` 必須） |
| POST | `/api/workspaces/{slug}/knowledge/chats/{id}/messages` | 発言を足し、AI の返答（説明＋提案）を返して保存する（C8）。body は発言・冪等キー・今の編集欄の本文（任意、64KB まで） |
| POST | `/api/workspaces/{slug}/knowledge/chats/{id}/summary` | 会話の要約の案を返す（保存しない）。本人が編集して下書きの保存（既存の API）の `note` に入れる |

- ロジックは `services/knowledge_chat.py`。`api/` に置かない
- 規約の提案は、規約の下書きの保存 API（既存のチーム規約の画面）に渡せる形（ルールの JSON）で返す

## 5. 画面

- 仕様・スキル・指示書のエディタ（`KnowledgeEditor`）に「AI と作る」パネル。自分の会話の一覧、会話、提案の差分、「エディタに反映」
- 規約は既存のチーム規約の画面（別の API）に同じパネルを置き、提案はルールの下書きの編集欄に入れる。規約の会話は artifact に結び付かない（`kind=policy` で一覧する）
- パネルの最初に告知: 「会話は Google の Vertex AI（Gemini）に送られ、SpecLino の運用者は技術的に読めます。ほかのメンバーには見えません」
- 一覧画面に「チャットで新規作成」。会話で下書きを作り、保存した時点で知識（artifact）ができ、会話がそれに結び付く
- 保存のダイアログに「会話の要約を使う」。押すと要約の案が入り、本人が直して保存する
- 改訂の画面では、`note` を「変更の説明」として表示（要約で埋めたものはその旨を表示）
- 文言は既存にそろえる。「デモ」は使わない

## 6. 安全性

- 会話の本文と提案は持ち主にしか返さない（テストで固定: 同じワークスペースの owner でも 404）
- AI に渡すのは、文法の要約（仕様）、今の編集欄の本文、会話、ワークスペースの知識の名前の一覧（自分のワークスペースだけ）。他人の会話・他のワークスペースのものは渡さない
- 要約は保存前に本人が見る。自動で `note` に入れない
- 1 発言・1 会話の大きさ、1 日の発言数（ユーザーごと）に上限

## 7. 非目標

- 会話の共有（他人に見せる）
- AI による保存・承認・ゲートへの関与
- MCP / A2A からの会話（既存の `spec_suggest` と議論役で足りる）
- 規約 SPEC-TEST-001 を bundle の仕様に合わせる修正（別ストーリー S74）
