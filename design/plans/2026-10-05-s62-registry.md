# S62 知識レジストリの土台 — 実装計画（#104）

> 上位計画: `design/plans/2026-10-05-team-knowledge-registry.md` の S62。仕様: `design/2026-10-05-team-knowledge-registry.md` 3 章・7.1。
> 契約（Task 0）: `src/speclino/domain/knowledge.py` の名前・欄は変えない。

**目標:** skill / instructions / spec の改訂（draft → 承認 → active）と、承認・規約の有効化のたびに作る署名つき bundle を、DB・サービス・REST で提供する。S65（run の bundle 固定）・S66（エディタ）・S68（sync）が使う。

**方針:**

- 承認の流れは `services/policy_governance.py` を踏襲する（ワークスペース行のロック `TeamRepository.ensure_and_lock`、承認者 = `list_approvers`（owner / approver）、見た番号とハッシュの照合で `DraftConflict`、拒否の監査は独立トランザクション、作者本人の承認は `self_approved=True`）
- `DraftConflict` は `policy_governance` のものを再利用する。`policy_governance` からは `build_bundle` を関数内で import する（循環 import を避ける）
- bundle の署名は HMAC-SHA256。鍵は `Settings.bundle_signing_key`（`SPECLINO_BUNDLE_SIGNING_KEY`）。未設定なら env=local は固定の開発鍵、env=prod は起動時（`build_state`）にエラー
- 署名対象は `Bundle.model_dump(mode="json", exclude={"signature"})` の正規 JSON（`sort_keys=True, separators=(",", ":")`）
- `scope_hash` = 各メンバーの artifact_id → scope の正規 JSON の sha256
- 競合: スコープが重なる（workspace スコープは全てに重なる）同じ target の instructions、同名（frontmatter の `name`、無ければ artifact 名）の skill、spec の要求 ID（`compiled.requirements[].id` と `legacy_ir[].rules[].id`）の重複
- テストの置き場は既存の構成に合わせる（`tests/integration/services/`。DB の fixture と後片付けを共有するため）。上位計画の `tests/services/`・`tests/api/` からの逸脱として報告する
- REST の接頭辞は契約どおり `/api/w/{slug}`（既存は `/api/workspaces/{slug}`。差は報告する）
