# S68: スキルと指示書の配信（sync・lock・MCP）実装計画

> 親計画: `design/plans/2026-10-05-team-knowledge-registry.md`（S68）。仕様: `design/2026-10-05-team-knowledge-registry.md` 3.1・7 章・8 章。Issue #109。

**Goal:** 承認済みの知識（skill / instructions / spec）を、開発者の checkout に `speclino sync` で書き出し、署名つきの `.speclino/lock.json` を残す。MCP から読み取りで引けるようにし、ゲート用に lock の鮮度を Finding にする関数を用意する（配線は S65）。

**Architecture:**

- `services/sync_tokens.py`: sync 専用トークン（`slsync_`、SHA-256 だけ保存、1 プロジェクトに限る、読み取り専用）の発行・一覧・失効・認証
- `services/knowledge_sync.py`:
  - サーバ側: `render_files(resolved, generation)`（書き出すファイルの組み立て）、`issue_lock(...)`、`fetch_for_sync(session, token, repo_id)`（`ensure_bundle` → `resolve_for_project` → 記録 `knowledge_fetches`）
  - クライアント側: `write_bundle(repo_root, files, lock)`（検証 → `.speclino/.tmp-*` に段階書き → 全部できてから `os.replace`、lock は最後）
  - ゲート側: `check_lock_snapshot(snapshot, lock_json, current, verify)` / `check_lock(repo_root, lock_json, *, current, verify)`（`KNOWLEDGE-LOCK-001`、mandatory）
- `api/routes/sync.py`: `/api/workspaces/{slug}/sync-tokens`（発行・失効は owner / approver、一覧はメンバー）と `GET /api/sync/bundle?repo_id=`（sync トークン）
- `cli_sync.py`: `speclino sync`（URL は `--url` か `SPECLINO_URL`、トークンは `SPECLINO_SYNC_TOKEN` だけ。引数では受けない＝履歴に残さない。`a2a-send` と同じ流儀）
- `mcp_server/server.py`: `BearerAuth` が MCP トークンと sync トークンの両方を受け、sync トークンなら「読み取りだけ・そのプロジェクトだけ」を request.state に載せる。`sync_status` / `spec_get` / `skill_get` を足し、`verification_start`・`context_get` は sync トークンを拒否

## 書き出しの形（サーバとクライアントの約束）

| kind | パス | 本文 |
| --- | --- | --- |
| skill | `.claude/skills/<name>/SKILL.md`・付属、`.agents/skills/<name>/` に同じもの | `skill_md` / `files` |
| instructions | `AGENTS.md`（agents_md）/ `CLAUDE.md`（claude_md） | 管理区画の中身。workspace スコープ → プロジェクトスコープ、各々 artifact 名順に連結 |
| spec | `.speclino/specs/<name>.md` | `markdown` |

- `<name>` は SKILL.md の frontmatter の `name`（無ければ artifact 名。bundle の競合検査と同じ）。`^[a-z0-9][a-z0-9-]*$` でなければ配信を拒否
- 管理区画: `<!-- speclino:begin bundle=<n> -->\n` + 中身（末尾改行に正規化）+ `<!-- speclino:end -->`。lock の `files` は通常のファイルなら書く bytes の sha256、`AGENTS.md`/`CLAUDE.md` は中身だけの sha256
- lock: `issued_at`=今、`expires_at`=+30 日、`members` はこのプロジェクトに当たるメンバー、署名は `bundle_signing.sign(canonical_json(lock - signature))`

## 鮮度の判定（`KNOWLEDGE-LOCK-001`）

| 状態 | verdict |
| --- | --- |
| lock が無い・壊れている・署名不一致・期限切れ・別のワークスペース/リポジトリ・ファイル改変/欠落・管理区画の不正・lock の世代が今より新しい | UNKNOWN |
| lock の世代 < 今の世代で、このプロジェクトのメンバーが違う（`current_members` を渡さないときは世代だけで判断＝保守的に REVIEW） | REVIEW |
| それ以外 | VERIFIED_IN_SCOPE |

## Tasks（TDD、タスクごとにコミット）

1. **sync トークン**: repository に `list_for_team`、`services/sync_tokens.py`（issue / list / revoke / authenticate）。統合テスト（owner/approver のみ発行・失効、他ワークスペースのプロジェクト不可、平文は保存しない）
2. **書き出しの組み立てと lock**: `render_files` / `issue_lock` / `lock_payload`（単体）
3. **write_bundle**: パス検証・symlink・ディレクトリ衝突・管理区画・前回 lock 由来の削除・失敗時に前の状態を保つ（単体。`test_sync_rejects_parent_path`、`test_sync_rejects_symlink_target`、`test_sync_keeps_outside_managed_block`、`test_sync_failure_keeps_old_lock`）
4. **check_lock**: Snapshot 経由（単体。`test_lock_stale_is_review`、`test_lock_tampered_file_is_unknown`、期限切れ）
5. **API**: sync-tokens ルートと `GET /api/sync/bundle`、`knowledge_fetches` の記録（統合。他プロジェクトの repo_id は 404）
6. **CLI** `speclino sync`（単体。ASGITransport で偽サーバ。トークンを出力に出さない）
7. **MCP**: sync トークンの認証、`sync_status` / `spec_get` / `skill_get`（統合。`test_sync_token_cannot_start_verification`）
8. 仕上げ: `make lint typecheck test`、報告

## 判断

- 受け入れテストの置き場所はリポジトリの流儀（`tests/unit`・`tests/integration`）に合わせる（brief の `tests/services/` ではなく）
- マイグレーションは足さない（0010 の表で足りる）
- `check_lock` の署名は brief どおり。精密な比較のための `current_members`・`repo_id` は省略可能なキーワード引数として足す（S65 が渡す）
