# チームの知識レジストリ（2026-10-05）

SpecLino の位置づけを改める。これまでの中心は「各リポジトリの `specs/*.md` を Spec IR にして Z3 で検査する」
ことで、規約はその脇にあった。今後は、**チームがコーディングエージェントに渡す知識（規約・スキル・指示書・仕様）を
SpecLino で改訂・承認し、MCP / A2A / CLI で配り、守られていることを決定的に保証し、観測できるようにする**。
Z3 の意味検証は、その保証の手段のひとつになる。

この文書は `2026-09-26-team-policies-and-dx.md` の 2 章（正本の置き場所）を置き換える。
S61（`s61b-approver-ids` ブランチの縮小版）は、承認者を GitHub ユーザー ID で照合する部分だけを残し、
PR の Approve とチェックのボタンによる仕様の承認は中止した（ユーザー判断 2026-10-05）。
判定モデル（4 値、verdict とゲートの分離、フェイルクローズ、open-world）は変えない。

## 1. 目的と成功条件

- 人が負担なく読める仕様を、**意味を変えずに**機械可読な仕様へ変換し、決定的に判定できる
- 仕様を書く作業は AI が支援するが、機械可読な形への変換は決定的な手法で行う
- 規約（コーディング規約、命名規則、API、エラーとレスポンスの形式、エラーメッセージの書き方）、スキル、
  AGENTS.md / CLAUDE.md、仕様の 4 種類を、SpecLino の画面で簡単に管理できる
- 各自のコーディングエージェントが MCP / A2A / CLI で SpecLino から知識を取り、実装がそれに沿っていることを
  ゲートで保証する。どの知識の組み合わせ（bundle）で作業・判定したかを観測できる
- **間に合わない・解析できない部分は UNKNOWN になるだけで、偽の VERIFIED_IN_SCOPE を出さない**（範囲を広げても守る不変条件）

## 2. 決定事項

| # | 決定 | 理由 |
| --- | --- | --- |
| D1 | 4 種類すべての正本を SpecLino に置く（仕様も Git から移す） | 1 つの改訂・承認・配信・観測の仕組みで済む。1 つの仕様を複数のリポジトリと組にできる |
| D2 | 仕様の機械可読な部分は 2 つの入口を持つ: **UML（Mermaid の厳格な部分集合）** と **旧形式（今の Spec IR の Markdown、v0.1）**。どちらも同じ IR に変換する。文章は判定に使わない | 図は構文が閉じているので決定的に読める。旧形式は図で表せない要求（後条件、禁止、正確な回数、claim scope）を持つので、失わずに残す |
| D3 | 図は クラス図・シーケンス図・状態遷移図・アクティビティ図（`flowchart`）の 4 種類 | 構造・手順・遷移・制御フローをそろえる |
| D4 | 入口 → IR の変換は決定的な parser。LLM は変換に関与しない | 同じ本文からは必ず同じ IR とハッシュが出る |
| D5 | AI ができるのは本文の差分の提案だけ | AI の出力を判定経路に入れない |
| D6 | 有効な改訂の集合を **bundle**（ワークスペースごとの連番のスナップショット）として固定し、run・sync・replay は bundle 単位で扱う | 承認の途中で混ざった集合を読まない。スコープの変更を統治する。再現性を 1 つの番号で表す |
| D7 | 配信は `speclino sync`（手元に書き出す＋署名つき lock）と MCP | エージェント本来の読み込み（スキル、AGENTS.md）に乗る |
| D8 | 規約の検査は 2 段階: プログラムの実行と構造は決定的な検査器、それ以外は LLM 支援（verdict は常に REVIEW） | 決定的に書ける部分は決定的に。LLM は合否を確定させない |
| D9 | 操作名とシンボルの対応（`bindings.yaml`）と免除（`exceptions.yaml`）はリポジトリに残す。対応は名前の一致を既定にし、例外だけ上書きする | どちらもコードと同じ PR で変わり、レビューされるべきもの |
| D10 | `policy_revisions` は移行しない。新しいテーブルは追加だけ。規約は既存の表のまま bundle から参照する | 本番での移し替えの危険（遅れた書き込みの喪失、rollback での分岐）を無くす |
| D11 | 仕様は先に承認し、実装は後 | D1 の帰結。仕様駆動開発の順序に合う |

## 3. データモデル

```text
Workspace（チーム。S53 のまま）
 ├─ Artifact（kind = skill | instructions | spec。名前はワークスペース内で一意）
 │    └─ ArtifactRevision（連番。draft は可変、active / superseded は不変。内容にスコープを含む）
 ├─ PolicyRevision（既存の policy_revisions。変えない）
 └─ Bundle（連番。ある時点の active な改訂の集合と、解決済みのスコープ）
Project（リポジトリ。最大 1 つのワークスペースに属する。S53 のまま）
```

| テーブル（すべて追加） | 内容 |
| --- | --- |
| `artifacts` | `id`、`workspace`、`kind`、`name`、`created_at`。(workspace, kind, name) で一意 |
| `artifact_revisions` | `artifact_id`、`revision`、`status`（draft / active / superseded）、`content`（JSONB。kind ごとの pydantic モデル）、`content_hash`、`author`、`approver`、`self_approved`、`note`、時刻。(artifact_id, revision) で一意、artifact ごとに active は最大 1 つ、draft も最大 1 つ（部分一意インデックス） |
| `bundles` | `workspace`、`generation`（ワークスペースごとの連番）、`policy_revision`、`members`（(artifact_id, revision, content_hash) の一覧）、`scope_hash`、`signature`、`created_at` |
| `llm_assessments` | 5.3 のキーと出力、試行ごとの結果 |
| `attestations` | 人の確定（指摘の指紋、内容のハッシュ、処置 attested / acknowledged_violation、誰が、いつ） |
| `knowledge_fetches` | sync・MCP からの取得（トークン、メンバー、bundle、時刻） |

### 3.1 改訂の内容（`domain/` に pydantic で定義）

| kind | content |
| --- | --- |
| `skill` | `SKILL.md` の本文（frontmatter の `name` / `description` を検証）、付属ファイル（相対パス → 本文。テキストのみ、1 ファイル 256KB・合計 1MB まで）、`scope` |
| `instructions` | `target`（`agents_md` / `claude_md`）、本文、`scope` |
| `spec` | Markdown の本文、`scope`（1 つ以上のプロジェクトが必須）、承認時に固定する IR・IR のハッシュ・parser の版 |

- `scope` は `{"projects": [...]}` または `{"workspace": true}`（skill / instructions のみ）。**スコープの変更は新しい改訂と承認を要する**
- 規約のスコープは今のまま（ワークスペースの改訂が全プロジェクトに当たる）

### 3.2 承認と bundle

- 承認できるのはワークスペースの owner / approver。**作者本人の承認は今の規約と同じく認め、`self_approved` を監査と画面に出す**（1 人で使う場合とデモのため）
- spec の改訂は、診断にエラーが 1 つでも残っていれば承認できない（サーバ側で拒否）
- 承認者が見た内容（番号と content_hash）でなければ拒否する（S43 と同じ楽観的な照合）
- **承認・規約の有効化のたびに、同じトランザクションの中でワークスペース行をロックし、新しい bundle を作る。**
  bundle を作るときに競合（同名の skill がスコープ内に 2 つ、
  spec の要求 ID の重複）を検査し、競合があれば承認ごと拒否する
- `artifact.workspace` とスコープのプロジェクトの `team` が一致することを、bundle を作るトランザクションの中で確かめる
- 監査: 作成・更新・承認・却下を `audit_events` に残す
- **取り下げ**: owner / approver は有効な改訂（見た番号と content_hash）を取り下げられる。行は消さず superseded にし（後継の active は作らない）、同じトランザクションで新しい bundle を作る。過去の bundle は不変。sync は次の取り込みで外れたファイルを `absent` として消す。戻すときは最新の改訂を土台に下書きを作って承認する。監査は `knowledge.retire`（理由・bundle の世代）

### 3.3 移行（取り込み）

- **規約**: 移行しない（D10）
- **仕様**: 各リポジトリの `specs/*.md` と `specs/ir/` を、取り込みコマンドで spec の改訂 1 として登録する。旧形式の
  入口（D2）で読むので、IR は失われない。図への書き換えは自動では行わない（人が移す。エディタで旧形式と図の両方を書ける）
- **ドメイン**: `.speclino/domain.yaml` は spec の内容の一部（`domain` 節）として取り込む。クラス図は語彙と構造を
  与えるが、入口の仮定・不透明な ID・観測の境界・対象外の宣言は `domain` 節に残す
- **リポジトリの規約** `.speclino/policy/*.yaml`: そのまま読み続ける（D10。D1 の例外として明記する）。チーム規約は今どおり SpecLino
- 自己検証（`make selfcheck`）は `tests/fixtures/selfcheck/` の凍結コピーで動かし続ける

## 4. 仕様: 決定的な変換

### 4.1 UML の入口: Mermaid の厳格な部分集合

「Mermaid 全般」ではなく、SpecLino が受け付ける部分集合を EBNF で固定する（`spec/uml/grammar.md`、parser の版つき）。

- 全要素に**明示的な ID** を必須にする。表示ラベルは ID に使わない（例: シーケンス図のメッセージは `A->>B: [m1] reserve(order)`、
  状態遷移は `PENDING --> PAID: [t1] pay [status == PENDING]`）
- 対応しない構文（`par`、`critical`、`rect`、`subgraph`、方向以外の directive、`click` 等）は**エラー**にする。
  コメント（`%%`）と見た目だけの要素（`direction`、ノードの形のうち意味を持たないもの）は**明示的に無視する一覧**に載せる
- **消費されないトークンが 1 つでもあればエラー**（全か無か）
- Mermaid として描画できるかと、SpecLino が意味を読めるかは、別の診断にする

| 図 | 受け付ける要素 | IR |
| --- | --- | --- |
| クラス図 | クラス、属性と型（int / bool / str / 列挙 / 不透明 ID）、`<<enumeration>>`、操作とシグネチャ | 語彙（`domain` 節と合わせる）、構造の義務 |
| シーケンス図 | 参加者（`participant X as Y` の alias を含む）、`->>`、`-->>`、`alt` / `else` / `opt` / `loop`、ガード、入口の操作の宣言 | 入口ごとの**順序の義務**（オートマトン） |
| 状態遷移図 | 状態、`[*]`、遷移（ID・イベント・ガード）、状態を持つ属性の宣言（注記） | **遷移の関係** |
| アクティビティ図 | `flowchart` の処理ノード、判断ノード `{}`、辺のガード、開始と終了、`closed: true` の宣言 | 1 つの操作の**制御フローのオートマトン** |

- **ガード**は今の `domain/expr.py` の式。参照は今と同じ `before.` / `after.` / `outcome.` の名前空間を必須にする（入口の引数は `before.` で表す。
  例 `[before.inventory.stock < before.order.qty]`）。自然言語のガードはエラー
- **要求の表**は機械可読な形式（`| ID | level | 要求 | 形式化 |`）。`形式化` 列は `図ID#要素ID` か `ir:要求ID`。
  これは判定ではなく**追跡**に使う: 参照の無い行は「未形式化」

### 4.2 旧形式の入口

今の Spec IR の Markdown（v0.1。`条件` / `期待する結果` の節と `specs/ir/*.json`）をそのまま読む。LLM の抽出器
（`spec/spec_extractor.py`）は廃止し、IR は承認済みの JSON を正とする。エディタで IR の JSON と本文を並べて編集できる。

### 4.3 変換の性質（テストで保証する）

- **決定的**: 同じ本文・同じ parser の版からは同じ IR とハッシュ（LLM・ネットワーク・時刻に依存しない）
- **全か無か**: すべてのトークンが、IR の要素・明示的に無視する要素・エラーのどれかに分類される（トークンの網羅テスト）
- **往復**: `render` は IR から正規形の Mermaid を作る。`parse(render(parse(s))) == parse(s)` を性質テスト（hypothesis）で保証する
- **意味の確認は人が行う**: エディタは原文と正規形を並べて表示し、承認者は両方を見て承認する
- 変換は `spec/uml/` に置き、LLM と adapters に依存しない（import 制約テストに加える）。IR と manifest に parser の版を残す

## 5. 仕様の検査

### 5.1 共通: オートマトンと解析の精度

- 図（シーケンス・状態遷移・アクティビティ）は有限オートマトンに変換する（`TraceObligation`。`domain/` に型、`conformance/` に検査）
- path_analyzer の経路ごとのイベント列（Code IR の `Event` の `sequence` 順）とオートマトンの積を取り、
  ガードは経路条件と合わせて Z3 で充足可能性を確かめる
- **VIOLATED / VERIFIED_IN_SCOPE を出してよいのは、`precision=exact_in_model` の経路だけ**。不完全な経路、
  不透明な領域、一般の `while`、展開できない `for`、経路数の上限超過（既定 64）は UNKNOWN
- 対応が見つからない要素（名前が一致せず `bindings.yaml` にも無い）は UNKNOWN

| 義務 | 検査 | open-world との関係 |
| --- | --- | --- |
| 構造（クラス図） | クラスとメソッドが存在し、引数の数と名前が合うか（AST。import しない） | 図に無いクラスやメソッドがあっても問題にしない |
| 順序（シーケンス図） | ガードが成り立つ経路のイベント列が、図の呼び出し列を**部分列として含む**か。`loop` は 0 回以上として読む | 図に無い呼び出しが間にあっても違反にしない |
| 遷移（状態遷移図） | 状態の属性への代入ごとに、経路上の前の状態から許された遷移か | 宣言した属性だけを見る |
| 包含（アクティビティ図） | 経路のイベント列が図のどれかの道筋に沿うか | **`closed: true` の図だけ**、図に無い処理を VIOLATED にする。それ以外は REVIEW |

#### 5.1.1 図の名前とコードの対応（S83）

SpecLino の処理の多くはクラスではなくモジュールの関数（`async def` を含む）で、メソッドは属性経由
（`self.registry.execute`）で呼ばれる。図をそのまま照合できるよう、対応を次の順で決める。どの段も決定的で、
決まらないもの・一意でないものは写さず UNKNOWN にする（偽の VERIFIED / VIOLATED を出さない）。

| 対象 | 規則 |
| --- | --- |
| モジュール（`<<module>>`、grammar.md 4 章） | `bindings.yaml` の `modules`（名前 → 完全修飾のモジュール名）、無ければ `<名前>.py` / `<名前>/__init__.py` が source_roots に 1 つだけのとき。操作 = モジュール直下の `def` / `async def`。候補が複数・動的な定義（`__getattr__`・`exec`・`globals()`・同名の代入や import・条件付きの定義）があれば UNKNOWN |
| 図の操作 `<C>.<m>` | `bindings.yaml` の operations（キーの一致 → シンボルの末尾の一致）。無ければ**名前の一致**: `<C>` をクラス図のステレオタイプに従って一意なクラス（モジュール）として探し、`<m>` が定義されていればその完全修飾名を操作にする（操作 ID は図の名前）。末尾の一致が複数なら名前の一致に進まず UNKNOWN |
| 入口 `%%@ entry` | `bindings.yaml` の behaviors（キー → entrypoint の末尾の一致）、無ければ同じ名前の一致で入口を作る。名前の一致で作った入口は変数の対応を持たない |
| 呼出し | 呼出しの候補は「別名を展開した属性チェーン」（従来、`self.registry.execute`）と「宣言型で解決した完全修飾名」（`pkg.mod.ToolRegistry.execute`）。bindings のシンボルはどちらで書いてもよい。候補が別々の操作に当たれば未解決（その操作に触れる義務は UNKNOWN） |
| ガードの変数 | 型環境は仕様の domain にクラス図の列挙と属性の変数（`triage.has_findings`）を足したもの。値の対応は behavior の `variables` に**図の変数名で**書く（旧形式の名前 `has_findings` と並べてよい。解析はその検査の domain にある変数だけを使う）。ガードが対応の無い変数を参照すれば UNKNOWN（経路条件と無関係な自由変数になり、偽の判定になるため）。1 つの実装に domain の変数が 2 つ当たれば解析しない |
| 遷移 | 状態の属性を `variables` に持つ behavior を検査する。持たない behavior が、到達し得るモジュール（import を推移的にたどった範囲）で同じ名前の属性に代入する（`x.<名前> = …`・`setattr`）なら、その behavior について UNKNOWN（図に無い遷移を見逃さない） |
| 名前の一致で写した操作の効果 | bindings で宣言した操作は従来どおり効果を仮定しない（契約が無ければ呼出しイベントだけ）。名前の一致で写した操作は宣言が無いので、イベントを出したうえで本体も展開する（メソッドなら `self` に受け手を束縛）。展開できなければ効果を確定できない未解決（UNKNOWN） |

宣言型（`analysis/static_types.py`）の根拠は、引数の注釈・メソッドの `self`・`__init__` の中の
`self.a = <注釈つき引数> / T(...)` / `self.a: T = ...`（すべて同じ型のときだけ。ほかのメソッドやクラス本体で書かれる
属性は型なし）・戻り値の注釈だけ。宣言型で解決したメソッドは操作の照合にだけ使い、名前の一致で写した操作を除いて
本体を展開・走査しない（`self` の束縛が無いと引数がずれるため）。

前提（検査の範囲。Finding の観測境界にも同じ前提が入る）:

- **注釈は実行時の値と整合する**: 戻り値・引数・属性の注釈を信じる（`make_tool() -> Tool` が実際は `None` を返す、のような
  食い違いは見ない）。注釈の整合は mypy strict で保証されたリポジトリを前提にする
- **実行時のサブクラスの上書きは区別しない**（「宣言型の操作の呼出し」として扱う）
- **属性の読み出しは純粋**: 経路の解析が従来から置いている前提（プロパティ・`__getattr__` の効果は見ない。PoC 3.2 の
  「単純な属性」）。自明な構築・純粋な標準関数の引数も、名前・定数・属性の読み出しだけのときに限る（呼出し・await・
  添字・演算子があれば未解決）

自明な構築: 基底・デコレータ（メソッドのものを含む）が無く、`__init__` が `self.x = <引数か定数>` だけのクラスの構築は
副作用なしとし、イベントも未解決要因も作らない。

構文の追加（PoC 3.2 の部分集合の拡張）: `assert t, m` は「t が偽なら `AssertionError` で抜ける」分岐（`python -O` の実行は
モデルの外）。分解代入は対象が名前だけのとき（右辺が同じ長さのタプルなら要素ごと、呼出しなら呼出しを解析して各名前は
値の分からない結果）。`return None` は `return`。副作用の無い標準の関数（`len`・`isinstance`・`str`・`int`・`bool`・
`repr`・`abs`・`json.dumps`・`json.loads`。組込みの名前はモジュールで再束縛され得ないとき）は呼出しを未解決にしない
（結果の値は追わない）。

`await f(...)` は f の呼出しとして扱う（呼出し元の順序は変わらない。await の間に他のタスクが入口の引数の属性を
書き換えることはモデルの外）。`async def` を await せずに呼ぶ、同期関数の結果を await する、呼出し以外を
await する、はどれも未解決。`async with` / `async for` は従来の `with` / `for` と同じく不透明な領域として扱う。

S82 のシステム全体の仕様 7 本で確かめた結果、構造の義務と、条件が入口の値で書ける振る舞い（ゲートの決定、
ツールの関門）は判定まで出る。DB を扱うサービス関数の振る舞いは、分岐の条件が DB の問合せの結果（`is None`、
`in` など）で入口の値に対応づけられず、本体もトランザクション（`async with`・`try`）の中にあるので UNKNOWN に残る
（仕様の観測境界に明記する）。複数の要求にまたがる流れと、DB の行が持つ状態は図（検査の義務）にせず表で書く。

### 5.2 期待する Finding の列挙

run は、bundle から導いた「出るべき要求 ID の一覧」を manifest に書く。検査の後、一覧にあるのに Finding が無い要求には
UNKNOWN の Finding を合成する（`missing_finding`）。規約の検査器・LLM 支援・仕様のすべてに適用する。
ゲートが「出てきた Finding だけ」で判定して、出なかった必須の要求が素通りする穴を塞ぐ。

## 6. 規約

### 6.1 決定的な検査器

プログラムの実行と構造に関わる規約。今の検査器レジストリに足し、パラメーターは規約の改訂に持たせて画面のフォームで編集する。

| 検査器 | 入力 | 検査すること |
| --- | --- | --- |
| `api.error_format`（既存を拡張） | OpenAPI、Python の AST | 今の内容に加え、成功時の包み方（エンベロープ） |
| `api.conventions`（新規） | OpenAPI、FastAPI のデコレーター（AST） | パスの命名（ケース、複数形、版の接頭辞）、使ってよいメソッド、`response_model` の有無 |
| `naming.identifiers`（新規） | Python の AST | 関数・クラス・定数・モジュールの名前が正規表現に合うか、禁止語 |
| `error_message.format`（新規） | 例外やエラーレスポンスに渡す文字列リテラル（AST） | テンプレート、エラーコードの有無、文末、使う言語 |
| `lint.preset`（新規） | リンターの設定ファイルと CI の定義 | チームのプリセットのルールが有効で、CI で実行されているか |

### 6.2 LLM 支援

- 規約のルールに `tier: llm_assisted` を足し、検査器 ID は `llm.checklist`（パラメーターにチェック項目の一覧）とする。
  `PolicyRule` の「mandatory には検査器が必須」の検証はそのまま通る
- **verdict は常に REVIEW**。指摘の有無は別の属性 `assessment_outcome`（`issue` / `no_issue` / `split`）で表す。
  指摘には根拠の引用・場所・チェック項目を必ず付ける
- mandatory なら REVIEW でゲートは止まる。人の確定は verdict を書き換えず、**ゲートの処置**として `attestations` に記録する
  （`attested` → その指紋の REVIEW をゲートの阻止から外す、`acknowledged_violation` → 阻止したまま）。確定は指紋と内容のハッシュに
  結びつき、内容が変われば効かない。確定できるのはワークスペースの owner / approver（画面、または S61 縮小版の ID 照合を通した PR コメント）
- **まとめて確定する経路**: ハッシュつきの `/speclino attest` を 1 件ずつ打つ手間を省くため、承認者の次の 2 つを
  「その PR の最新の検査の確定できる要確認すべてを attested で確定する」依頼として扱う（`attest_all_in_pr` で共通）
  - 引数なしの PR コメント `/speclino attest`（`via` は `pr_comment_all:<URL>`）。1 人運用（作成者＝承認者）では GitHub の
    制約で自分の PR を Approve できないため、こちらが主の経路
  - GitHub の PR の Approve（`pull_request_review` の `submitted` かつ `state=approved` だけ。commented・changes_requested・
    dismissed は無視。`via` は `pr_review:<URL>`）
  - 照合・記録は 1 件ずつのコメントと同じ（`approver_ids` と GitHub のユーザー ID、`attest`。actor は `github:<ID>`、自己確定の印、
    対応表の変更の警告）。指紋と hash はサーバが run の Findings から取る
  - 対象はその PR の最新の run で、最新の完了した run と head が一致するもの（検査中・未検査のコミットがあれば確定しない）。
    Approve はさらに head が `review.commit_id` と一致するときだけ（古いコミットへの Approve で新しい変更を確定しない）。
    合わなければ何もせず、理由を webhook の応答と監査 `attestation.bulk` に残す（webhook は PR にコメントを書かない）
  - 確定するのは `attestation_target` が返すもの（VIOLATED などは対象外）。書込みは `INSERT … ON CONFLICT DO NOTHING` で、
    既に確定がある (指紋, hash) は上書きしない（重複の依頼は冪等、並行して保存された `ack` も覆さない）。確定が 1 件以上
    あれば同じ head で再検査し、ゲートのコメント・Check を更新する。新しい確定が 0 件でも、最新の完了した run に attested の
    確定が効いていない要確認があれば（再検査の投入に失敗した後の再送など）再検査を作り直す（未完了の run は superseded）
  - run を引いてから確定するまでの間の push（TOCTOU）は防がない: 確定は (指紋, 内容の hash) に結びつくので、push で中身が
    変われば別の hash の要確認になり、古い run の要確認の確定で新しい変更は素通りしない
  - 案内は「承認者が `/speclino attest` とコメントする（または PR を Approve する）と確定する」。1 件ずつのハッシュつきの形は
    ゲートのコメントの各指摘の「根拠」に畳んで出す
- 画面では `no_issue` を「LLM で確認、指摘なし（機械検証ではない）」と独自の区分で出す
- LLM を呼ぶ処理は `services/` に置き、`conformance/` は結果を Finding として受け取るだけにする（ARCH-002）

### 6.3 揺らぎを防ぐ

1. **評価の単位を固定**: 関数・文字列リテラル・エンドポイントの単位で評価する。キーは
   (規約の改訂, ルール ID, 正規化した単位の内容のハッシュ, モデル, プロンプトの版)。キーが同じなら LLM を呼ばず記録を返す
2. **指摘の同一性は内容で決める**: 指紋 = (ルール ID, シンボルのパス, 単位のハッシュ, チェック項目)
3. **出力を絞る**: チェック項目ごとに「該当する／しない＋根拠の引用」だけを構造化出力で答えさせる（temperature 0）
4. **初回は多数決**: 新しいキーは 3 回評価し、2 回以上一致した項目だけを `issue` にする。割れた項目は `split`
5. **replay は呼び直さない**: manifest に (キー, 出力) を記録し、replay は記録で再評価する

## 7. 配信

### 7.1 `speclino sync`

- 対象リポジトリに当たる最新の bundle を取得し、書き出す
  - スキル: `.claude/skills/<name>/` と `.agents/skills/<name>/`
  - 指示書: `AGENTS.md` / `CLAUDE.md` の管理区画（`<!-- speclino:begin bundle=<n> -->` 〜 `<!-- speclino:end -->`）。外は触らない
  - 仕様: `.speclino/specs/`（読み取り専用の写し）
- `.speclino/lock.json` に bundle の世代・各メンバーの (artifact, revision, content_hash)・書き出したファイルのハッシュ・
  サーバの署名・期限を書く。**lock の意味は「この checkout が宣言している bundle」であり、利用の証明ではない**
- 安全性: skill 名と付属ファイルのパスを正規化し、ルート外・絶対パス・`..`・symlink を拒否する。本文に管理区画のマーカーが
  含まれていれば承認の時点で拒否する。サイズ上限。書き出しは一時ディレクトリに作ってから置き換え、失敗したら前の状態と lock を保つ
- 認証: **sync 専用の読み取り専用・リポジトリ限定のトークン**（新設）。トークンを lock やログに出さない

### 7.2 MCP / A2A

- MCP: 既存の `context_get` / `verification_start` / `verification_get` に、`sync_status`（lock が最新か）、`spec_get`、
  `skill_get`、`spec_suggest`（AI の書き換え提案）を足す。読み取り系は sync 用トークンでも呼べ、検査の開始は既存のトークンに限る
- A2A: 既存の議論役に、仕様の下書きの相談を足す。返すのは提案（本文の差分）だけ
- 取得は `knowledge_fetches` に記録する（可観測性の材料）

## 8. ゲートと再現性

- run の開始時に bundle を 1 つに固定し、その run の中では再解決しない
- 仕様: 5 章の結果。規約: 6 章の結果。5.2 で欠けた要求を UNKNOWN で補う
- **鮮度**: PR の `lock.json` の署名を検証し、書き出したファイルのハッシュが lock と一致するかを確かめる。そのうえで lock の bundle を
  run の bundle と比べる。古ければ REVIEW、lock が無い・署名が合わない・ファイルが改変されていれば UNKNOWN。どれも必須扱い
- manifest に bundle の世代と全メンバーのハッシュ、parser の版、LLM 支援の記録のキー、期待する要求 ID の一覧を書く
- **replay は bundle を解決し、決定的な検査器と仕様の検査を再実行する**（今は規約の Finding を再評価していない。これを直す）。
  LLM 支援は記録で再評価する
